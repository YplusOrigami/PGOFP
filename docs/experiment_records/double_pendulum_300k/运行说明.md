# 倒立双摆 300k：MPC / PPO 先验扫描

准备日期：2026-11-18。正式矩阵只生成计划，尚未在本地启动训练。PID 不在本轮范围内。

## 实验配置

| 项目 | 配置 |
|---|---|
| 环境 | InvertedDoublePendulum-v5 |
| 先验 | CEM-MPC、冻结 PPO |
| β | 0、0.5、1 |
| Flow 训练 seeds | 0、1、2 |
| 每 run 训练预算 | **300,000 步**，不是 30,000 |
| 总计划 | 2×3×3=18 run，合计 5,400,000 个 Flow 环境步 |
| 并发 | **3 个独立训练进程**，共享当前可见的 CUDA 设备；每 run 一个环境 |
| PPO 先验 | 优先复用上一轮 seed100、实际 1,001,472 步的冻结 artifact；共享给所有 Flow seed |
| 日志 | JSONL、TensorBoard、配置、事件、逐回合评估、进度日志；WandB disabled，无需登录 |
| 先验评估 | 每个 run 开始前评估 10 回合并记录 return；PPO 同时记录随机执行与确定性执行 |
| Flow 评估 | 每 10k 步，10 回合随机执行 + 5 回合代表动作，seeds_base=10000；保留上一轮的额外最终评估 |
| 保存 | 每 10k 保存 last+replay；另保留 best、final，数值失败单独记录 |

其余学习配置与上一轮一致：5k 均匀动作热身、UTD=1、batch256、网络[256,256,256]、K_train/local=32/16、单步 K_exec/eval=1、固定 α=.1、Critic 熵项开启、Heun 密度估计5步、public_state、不输入控制器特征、σ_prior=.3、σ_base=1。MPC 保持 H10/P64/I4、seed0、0.5秒超时，不因并发改变控制器参数。奖励没有改写。

配置入口：[double_pendulum_prior_beta_300k.yaml](../../../configs/experiment/double_pendulum_prior_beta_300k.yaml)。

## 在服务器直接运行

在项目根目录运行：

```bash
bash launch_double_pendulum_300k.sh
```

**新脚本无参数就启动正式实验。** 它复用已有依赖检查/缺失依赖自动安装和 TensorBoard 实际写入回读检查；默认 CUDA、并发3、本地日志，既有 CUDA PyTorch 会按原 bootstrap 规则保留。没有 CUDA 时明确失败，不悄悄用 CPU 跑正式矩阵。

输出默认是 `outputs/experiments/double_pendulum_prior_beta_300k_v1/`，与上一轮 `mujoco_30k_a100_v1/` 分开。根目录旧 `launch_mujoco_30k.sh` 保持原有“无参数只生成计划”的行为；本说明中的新脚本默认行为不同。

推荐在服务器现有 tmux 会话运行，或先创建：

```bash
tmux new -s double300k
bash launch_double_pendulum_300k.sh
```

使用 Ctrl+b，再按 d 脱离会话；之后 `tmux attach -t double300k` 返回。训练不能依赖 SSH 终端持续连接。

默认优先复用：

`artifacts/priors/mujoco_prior_beta_30k_v1/inverted_double_pendulum_ppo_seed100/stage_1000000`

本地现有 artifact content hash 为 `5e9e89068316fda9691be6aecb056bc006055d01dfba76af5c184016b227014b`。运行时检查环境、seed、预算、内容校验和和 smoke 标记；registry 保存实际使用的完整 hash。若指定的历史 bundle 不存在，使用新批次目录制备 seed100、约百万步 PPO，不覆盖历史先验，也不跳过 PPO 组。PPO 制备仍单任务准备，完成后才启动 Flow；本轮只有一个 PPO 制备任务。

中断后在同一目录重跑相同启动命令：完成 run 保留，尚未运行的继续排队；有 last checkpoint 的中断 run 按 episode_restart 恢复。MuJoCo 的恢复不保证逐步轨迹完全一致。数值失败保留，不自动重试；β=1 的历史数值失败不应被成功样本替换。配置改变时需另建输出目录，不能修改历史证据。

并发3指 Flow 任务并发，不是每个 run 同时跑三个 seed，也不是三个环境合并成同一 agent。队列通常先启动同一先验/β 的 seeds0/1/2，空出一个 slot 就补下一个任务。MPC 的墙钟超时与负载相关，观察 `prior/fallback_rate`；该项与训练 NaN 退出分别记录。

## 结果文件与读取口径

- `plan.json` / `resolved_configs/`：正式计划300k×18，默认并发3。
- `preflight.json`：真实启动时保存最终 device、并发和单 run 预算，便于排查实际排程。
- `prior_registry.json`：冻结 PPO 的路径、hash、实际预训练步数。
- `manifest.json`：每个 run 的状态、开始/结束时间、退出码、恢复记录。
- `logs/`：按 run 保存完整终端日志；父进程显示6阶段、任务进度、出错阶段和日志路径。
- `runs/<run_key>__<id>/`：完整配置、JSONL、TensorBoard、events、progress、先验评估、逐回合 Flow 评估、检查点/replay。
- `summary_seed_level.csv` / `summary.csv`、`failures.json`、`verification.json`：原有聚合、失败与本地记录验收。

原有聚合器中的 `final_tail_return` 是末20%评估点的均值；300k 时不能当成最后一次300k回报。严格终点分数读取成功 run 的 `manifest.summary.final_eval` 或最后一次300k评估。失败 run 的最后有效评估不是300k终点。聚合统计和绘图时保留全部原始记录、按 seed 汇总，并注明随机/代表动作与评估回合数。

训练 checkpoint/replay 按现有 Git 规则留在服务器；JSONL/TensorBoard/配置及冻结正式先验沿用原跟踪规则。新脚本不修改这些规则、不上传 WandB。
