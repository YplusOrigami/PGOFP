# MuJoCo 30k 服务器运行效率排查

排查日期：2026-11-18。只读取已同步的 150 个 run、阶段进度日志和代码；未启动训练，未改训练算法、超参或启动器默认值。

**已确认这轮是串行实验：最大实际并发为 1，每个 run 仅一个环境，PyTorch CPU 线程数为 1。** 默认安排没有在短验证后继续做吞吐校准，偏向保守的显存使用，没有充分利用服务器的多任务吞吐能力。CPU/GPU 约 20% 的观察与此相容；但日志不足以把剩余 80% 换算成可兑现的 5 倍加速。

## 1. 这轮到底怎样并行

| 层次 | 当前实现与本轮证据 |
|---|---|
| PPO 先验制备 | 六任务在 `prepare_priors()` 的循环中逐一准备；HalfCheetah 复用已有先验，其余五个各约百万步。`run_logged()` 等当前子进程结束才继续。 |
| Flow 任务之间 | CLI 的 `--max-parallel` 默认 1。原始 manifest 的 150 组开始/结束时间复算，最大同时运行数确实为 1。 |
| 一个 Flow run 内 | `train.num_envs=1`；先 CPU 环境采样，再 GPU 更新，串行交替。没有异步采样队列。 |
| CPU 算子 | Shell 默认 OMP/MKL 线程均为 1；150 个 run 的 provenance 均记录 `torch_threads=1`。它限制的是相应算子线程，不代表系统绝对只能用一个 CPU 线程。 |
| MuJoCo 环境池 | `SyncEnvPool`，`step_slot` 在 Python 列表循环中依次调用。单纯增加 num_envs 不会自动获得环境子进程并行。 |
| MPC 规划 | CPU MuJoCo rollout，当前只有一个 `MjData`，没有配置多工作线程的 rollout 池。 |

排程代码：[benchmark_suite.py](../../../src/pgofp/experiments/benchmark_suite.py)（默认并发位于 main，先验串行位于 prepare_priors）；[启动脚本](../../../launch_mujoco_30k.sh)；[Launcher](../../../src/pgofp/experiments/launcher.py)。

150 个 Flow 子进程占用时间合计 **94.7547 小时**，从首个启动到最后退出跨度 **94.7781 小时**；相邻任务之间空隙总计约 **84 秒**（时间戳为秒级）。因此主要问题是“同时只安排一个任务”，并非 launcher 在两次任务之间长时间空等。先验准备在此之前，五个新先验的 artifact 预算计时另有 **7.72 小时**；这不是包括安装、失败尝试、所有收尾开销的完整端到端计时。

## 2. 94.75 小时花在什么地方

根据每个 run 的 `progress_events.jsonl`，把相邻时间戳的区间归属于前一个阶段。下表覆盖整个 Flow 子进程时间；阶段名是**主机墙钟阶段**，不是独占 CPU/GPU 运算时间。

| 阶段 | 合计小时 | 占子进程时间 |
|---|---:|---:|
| 正式训练循环（环境采样、控制器查询、模型更新及循环开销） | 80.43 | 84.9% |
| 前 5k 步热身采样 | 4.37 | 4.6% |
| Flow 周期评估及最终评估 | 8.51 | 9.0% |
| 每个 run 前的先验随机/确定性评估及结果记录 | 0.57 | 0.6% |
| 保存检查点阶段 | 0.034，约 2 分钟 | 0.04% |
| 进程构建、初始化与退出等 | 0.84 | 0.9% |

细分的 `timing/*` 日志另累计记录：collect 约 **28.54h**、update 约 **54.85h**、eval 约 **3.65h**、checkpoint 约 **33 秒**。这套计时在日志点 flush，失败末尾、30k 末尾及最终收尾存在未 flush 的窗口，且 `sync_device_timing=false`，不能把它当成完整 GPU 时间；应与上表区别。特别是它少记了部分评估，不能用 3.65h 替代全批的 8.51h。

本轮 Flow 实际训练交互 **4,151,270 步**，另有约 **2,216,709 步 Flow 评估**和 **1,529,340 步直接先验评估**。评估环境交互合计约 **374.6 万步**，没有记入 30k 训练预算。时间占比仍取阶段日志，不能仅按环境步数推算。

因此本轮不能归因于 WandB 上传（已 disabled）；先验基线和检查点也不是主要时间来源。用户要求的每次训练前先验评估不应为提速而删掉。

## 4. 单个 run 的明确开销和待验证热点

### 4.1 CPU 环境与 GPU 交替，小批量同步频繁

采样路径为：CPU 观测 → GPU 单样本 Flow → `action.cpu().numpy()` → CPU MuJoCo/先验 → CPU replay → GPU minibatch。冻结 PPO 控制器本身也在 CPU 计算。代码见 [collector](../../../src/pgofp/training/collector.py)、[replay_buffer](../../../src/pgofp/data/replay_buffer.py)、[PPO controller](../../../src/pgofp/controllers/ppo.py)。

这样的依赖链可以同时表现为多核 CPU 总使用率不高、GPU 使用率也不高。它不代表没有启用 GPU：本轮 Flow 配置均为 CUDA。CPU 面板是否按整机、分配核数或容器配额归一化，原日志未记录。

### 4.2 每次更新做大量诊断标量回传

[objectives.py](../../../src/pgofp/algorithms/objectives.py) 的 Critic 指标和 `_metrics()` 在每次更新中调用许多 `float(cuda_tensor)`，包含均值、分位数等；梯度范数及数值检查也有取主机值的路径。训练循环随后才按 log_interval 汇总输出，因此把 TensorBoard 关掉或单纯调大 log_interval，并不会自动去掉这些逐更新计算和同步。

读取 GPU 标量/拷回 CPU 会引入同步依赖；CUDA 的异步执行、拷贝同步及计时要求见 [PyTorch 2.14 官方说明](https://docs.pytorch.org/docs/2.14/notes/cuda.html#asynchronous-execution)。这是明确的同步候选，**尚未用远程 profiler 测得其耗时比例**，不能直接宣称它占了全部 update 的某个百分比。

### 4.3 “单步策略”只描述执行，不表示训练很便宜

完整 30k run 有 **25,001 次梯度更新**，batch=256。每次 Actor 更新含 32 个逆向候选和 16 个局部候选，即 256×48 个候选上的 Q/目标计算，并包含 MeanFlow JVP。Critic 熵项使用 5 步 Heun 密度反演，每次约 10 次向量场求值及散度计算。单步部署 K_exec=1 不会消除这些训练开销。

全批实际约 **340 万次更新**，而非只做了 415 万次轻量动作前向。代码见 [objectives](../../../src/pgofp/algorithms/objectives.py)、[MeanFlow target](../../../src/pgofp/math/meanflow_target.py)、[密度积分](../../../src/pgofp/math/integration.py)。

### 4.4 MPC 是独立的 CPU 规划成本，β=0 也仍在支付

本轮两个 MPC 的解析配置均为 H=10、P=64、CEM iterations=4，每次预测约 2,560 个模型控制步，还要乘环境 frame_skip 才是物理积分步。当前 planner 传入单个 MjData，没有使用多线程 rollout 池。原生 rollout 支持多工作数据及线程池，需按项目所装版本验证接入，见 [MuJoCo 官方说明](https://mujoco.readthedocs.io/en/stable/python.html#rollout)。

MPC 在采样/评估的控制器查询处计算；训练 minibatch 使用 replay 已缓存的先验，没有对 256 个 replay 样本逐个重新规划。已 flush 的两组 MPC collect 计时合计约 **22.27h**，说明采样路径规划成本确实很重。β=0、固定源且不输入控制器特征时，源数学上已退化为高斯，但 collector/evaluator 仍查询 MPC；因此存在可优化的无用规划。

### 4.5 评估和 30k 末尾重复工作

一个完成 run 做 10k/20k/30k 周期评估，结束时又做一次 30k 最终评估；每次 10 回合随机动作加最多 5 回合代表动作。完成 run 总计 60 个 Flow 评估回合。30k 周期保存 last 后，收尾又保存 last/final。重复评估比重复保存更值得处理；本轮的 30k 最后一次评估是主指标，优化后必须明确新协议，不能把旧分数悄悄换成前一次。

双摆 MPC 控制较好的 seed 存活更长，评估会产生更多规划调用；因此“单 run 30k”并不限制全部模型调用和评估成本。

## 5. 下一轮怎样提高吞吐

1. **先校准独立 run 并发数。** 优先比较 1→2→3，再决定是否尝试 4。保留 num_envs=1 和训练超参，使用已有 `--max-parallel`，分别记录单 run 速度、全批总 steps/s、显存峰值、进程 CPU 和失败/回退。不能直接由“20%”推导可以无损开五个。20GB 是否足以放三个进程还缺少本轮显存峰值证据。
2. **PPO/PID 与 MPC 分开确定并发。** MPC 对 CPU 份额更敏感。当前 MPC 对一次查询有 0.5 秒墙钟超时，CPU 争用可能改变 prior_valid 并回退高斯，实际改变策略。必须对比 prior/fallback_rate；本轮已记录的 MPC 日志窗口最大回退率为 0。不要为提高面板占用率而改变控制器有效性。
3. **做一次覆盖真实更新阶段的 CPU/CUDA profile。** 使用现有服务器 checkpoint 或跨过 5k 热身的短测；仅测热身会严重高估速度。记录 Actor 候选/JVP、Critic 密度、诊断标量回传、数据拷贝、MPC 和评估；工具支持见 [PyTorch Profiler](https://docs.pytorch.org/tutorials/recipes/recipes/profiler_recipe.html)。确认平台 vGPU 的计算份额、CPU 配额和监控分母，检查是否启用了强制同步调试设置。
4. **优先优化同步及实现，保留学习协议。** 指标在设备侧累计、按现有日志窗口批量回传；保留必要的非有限值检查及失败证据。增加 MPC 原生 rollout 工作线程、为严格 β0/无控制器特征场景设计先验查询快速路径，并验证控制输出/源密度一致。不要直接靠减 K、减密度步数或减 MPC 迭代来宣称等价提速。
5. **减少重复评估并并行准备先验。** 下一批将 30k 周期评估与最终评估合为一次，明确协议版本；仍保留每次 Flow 前的先验评估。`--max-parallel` 当前仅控制 Flow 任务，**不会自动并行 prepare_priors**；后者需要另设制备并发。PPO 的 64×64 小网络、单环境、minibatch64 也应单独测 CPU 与 GPU，不预设 GPU 一定更快。

现有信息足以确定“排程偏串行、存在 CPU/GPU 同步与 CPU 规划开销”，不足以确定最优并行度或承诺 2/3/5 倍提速。优先指标是完成同等协议实验的墙钟时间与总吞吐，不是单独把利用率推到 100%。
